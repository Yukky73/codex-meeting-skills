# Meeting Follow-up Runner

`meeting-transcript-to-minutes` を実行して指定済みの `面談準備/` 原本を完成させた後、同じ原本を入力として次の3スキルをこの順序で実行する親ハーネス。

1. `meeting-create-gmail-draft`
2. `meeting-write-deal-history`
3. `meeting-post-slack`

明示的に呼ぶときは `$meeting-run-followup` を使う。「面談後フォローを一気通貫で」「議事録化からフォローまで」といった依頼も起動意図として扱う。

## 利用者ごとの設定

実行前に [共通設定](../meeting-run-followup/references/configuration.md) を読み、作業ワークスペースの `.meeting-skills.local.md` を確認する。必要な設定が未記入なら、その段階を実行せず不足項目を示す。設定・議事録・承認内容はローカルで扱い、公開リポジトリへ保存しない。相対的なリソースパスは、このスキルの実体ディレクトリを基準に解決する。

## 承認モデル

- 議事録の完成検証後、外部書き込みを始める前に、次の3段階の対象・宛先・本文範囲・Gmail添付一覧をまとめてユーザーへ提示し、1回の明示承認を取得する。
  1. Gmailの新規下書き作成（添付ファイル名・絶対パス・サイズ・選択理由を含む）
  2. HubSpotの新規 `MEETING_EVENT` 登録
  3. Slack `設定済み報告チャンネル` の新規下書き作成
- ユーザーが承認した場合、その承認は提示した対象・本文・添付資料に限って3段階すべてに適用する。承認後はサービスごとの追加確認を挟まず、Gmail → HubSpot → Slackの順に自動実行する。
- HubSpotには、現行チャットで一括承認済みとして `confirmationStatus=CONFIRMED` を渡す。Gmailには一括承認済みの宛先・本文・添付一覧を、Slackには一括承認済みのチャンネル・本文を渡す。
- 承認前、対象・宛先・本文範囲・添付一覧または添付ファイルの内容が変わった場合、またはユーザーが一部だけを承認した場合は、外部書き込みを実行しない。変更後の対象をまとめて再提示し、承認を取り直す。
- コネクタがこの承認を受け付けず書き込みを拒否した場合は、別経路や回避操作を使わず、その段階で停止して報告する。

## 入力

- 対象は、ユーザーが明示した `面談準備/*.md` の原本1件だけとする。
- 文字起こしが会話に貼り付けられた、または入力ファイルが明示された場合は、それを議事録化ステップへ渡す。明示がなければ、議事録化スキルが tldv を照合する。
- 原本または文字起こしの対応を一意に決められない場合は、何も後続処理を実行しない。
- 「新規の面談記録」「新規の面談議事録」として作成された原本は、過去の会議・活動履歴を候補として照合しない。ユーザーが文字起こしを明示するか、原本に実施済みであることが示されるまで、このハーネスは議事録化以降の外部書き込みを実行しない。

## 実行方式

各段階は、この Codex Desktop の親セッションで直列実行する。`codex exec` の子セッションには接続済みアプリのコネクタと認可状態が引き継がれないため、子セッション・ブラウザ操作を代替経路として使ってはならない。

親セッションでは、接続済みの tldv、Gmail、HubSpot、Slack の各コネクタを直接使う。文字起こし本文は議事録化に必要な範囲だけ読み、後続の各段階には完成した原本を議事録内容の根拠として渡す。Gmail段階には、子スキルの添付基準で選択・確認した送付資料と、一括承認済みの添付一覧も渡す。

1. `$meeting-transcript-to-minutes` で対象原本を更新する。
2. 次の4見出しがこの順序で存在し、`面談情報`、`議事録`、`ネクストアクション` に実質的な内容があることを検証する。
   - `## 面談情報`
   - `## 議事録`
   - `## ネクストアクション`
   - `## 面談事前情報`
3. 検証に通った場合、`meeting-create-gmail-draft` の [添付基準](../meeting-create-gmail-draft/references/attachments.md) を読み、通常のプロダクト案内・基本料金表（ユーザーが明示指示した場合だけ特別料金表へ変更）と、必要に応じたセキュリティ資料を選択する。実在・読み取り可否・PDF形式・サイズ・SHA-256を確認する。料金表が判断不能なら推奨候補と理由を提示して選択を得る。Gmail下書きの宛先・件名・本文・添付一覧と選択理由、HubSpot登録の取引・本文・関連付け、Slack下書きのチャンネル・本文からなる一括承認内容を提示する。ユーザーの明示承認を取得するまで、外部サービスへ書き込まない。
4. 一括承認後、`$meeting-create-gmail-draft` を実行する。正常終了した場合だけ、`$meeting-write-deal-history` を実行する。
5. HubSpot段階が正常終了した場合だけ、`$meeting-post-slack` を実行する。Slack段階は公開チャンネル向けにメールアドレスを除外する。電話番号・住所・個人識別番号・金融情報・健康情報など、子スキルで禁止する個人情報が残る場合は、下書きを作成せず停止して報告する。一括承認後は、各子スキルで追加確認を求めない。

各段階の書き込み後には、外部サービスから本文を再取得して改行構造を検証する。Gmail は宛名・段落・署名と承認済み添付の件数・ファイル名・MIMEタイプ・バイト数、HubSpot は見出し・段落・箇条書き、Slack は原本の各行と空行を照合する。Gmail添付が不足・不一致・確認不能の場合、またはいずれかで一行への連結または空行の欠落があれば、その段階を失敗として後続を実行しない。

## 停止条件

- いずれかの段階が失敗した場合、失敗した段階以降は実行しない。自動再試行もしない。
- 議事録の照合不能、更新不能、または完成検証の失敗時は、外部サービスへ一切書き込まない。
- 一括承認が得られない場合、外部サービスへ一切書き込まない。
- 各子スキルが前提不足、重複、未認証などを理由に成果物を作成しない場合は、その子スキルの報告を保持し、親ハーネスは推測や代替操作を行わない。
- Gmail の送信、Slack の投稿、既存レコード・既存下書きの更新は行わない。

## 呼び出し方法

会話から `$meeting-run-followup` を呼び出し、対象原本を明示する。外部連携をシェルの子セッションから起動しない。

## 報告

親ハーネスは段階ごとの成功・失敗・未実行を示し、各子スキルが返した原本パス、HubSpot URL、Gmail下書きURL、Slack下書きURLをそのまま報告する。実行ログや文字起こしをファイル保存しない。
