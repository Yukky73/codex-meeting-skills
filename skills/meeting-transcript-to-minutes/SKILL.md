# Transcript To Minutes

`../meeting-create-minutes/assets/meeting-minutes-template.md` を正本とし、既存の `面談準備` 原本を更新する。

## 利用者ごとの設定

実行前に [共通設定](../meeting-run-followup/references/configuration.md) を読み、作業ワークスペースの `.meeting-skills.local.md` を確認する。必要な設定が未記入なら、その段階を実行せず不足項目を示す。設定・議事録・承認内容はローカルで扱い、公開リポジトリへ保存しない。相対的なリソースパスは、このスキルの実体ディレクトリを基準に解決する。

## 入出力

1. ユーザーが貼り付けた文字起こしまたは入力ファイルを明示した場合は、それを使い、tldv は検索しない。それ以外は、指定された原本、または会話上で一意に参照できる原本を使う。原本が一意でなければ更新せずに確認する。
2. 原本の `## 面談情報` から会社名、面談日、担当者名、クアンド参加者を読む。旧形式では `◆商談概要` を照合用に読む。
3. 接続済みの tldv コネクタで会社名を検索し、面談日、担当者名、会議タイトル、参加者で照合する。照合済み候補が複数ある場合だけ最新日時を採用する。対応を一意に決められなければ、候補の日時・タイトル・参加者を示して確認する。tldv の Web サイトをブラウザで開く操作は行わない。
4. tldv コネクタが利用不可、未認証、または文字起こしを取得できない場合は原本を変更しない。別サービス、ブラウザ、記憶にある会議内容で代替しない。
5. 文字起こしは直接読み、入力用ファイルや実行ログを保存しない。

## 議事録の更新方針

1. テンプレートの見出し順を保つ：`## 面談情報`、`## 議事録`、`## ネクストアクション`、`## 面談事前情報`。
2. 更新対象は最初の3セクション。`## 面談事前情報` は保持し、`## 面談情報` は文字起こしで明確に補強できる項目だけ更新する。
3. 旧形式の原本は、`◆商談概要`、`◆議事録`、`◆ネクストアクション` の内容を対応する現行セクションへ移す。これらの既存情報を失わせず、旧 `◆` 見出しは残さない。

## `## 議事録` の書き方

明らかな誤字・脱字・話者取り違えだけを補正し、数値、固有名詞、人名、部署名や不明箇所は推測しない。打合せの発話順を再現するのではなく、後から提案を考える人が「どのような顧客で、どのような状態・制約・優先順位にあるか」を把握できるよう、情報の意味ごとに整理する。

最初に `【提案設計に関わる顧客理解】` を置き、重要度の高い事実を集約する。事業・現場・業務の実態、体制・役割・意思決定の構造、利用中の仕組み、課題が生じる条件、制約、予算・時期・優先順位、導入判断の基準、既存施策への評価を、文字起こしに根拠がある範囲で残す。単に「課題がある」とせず、誰が、どの業務で、どのような状況にあり、何が障害・判断材料になるのかを具体的に書く。これらの重要事項を会話の途中の小見出しだけに埋め込まない。

続いて必要に応じて `【課題と背景】`、`【検討状況と判断条件】`、`【提案への反応・確認事項】` などの独立行の小見出しと箇条書きを使う。1項目1情報を基本に、顧客の発言、反応、懸念、前向きさを中心に残す。提案の切り口や導入可能性は、顧客が明示した事実・反応・判断条件として記録し、議事録側で根拠のない提案方針や解釈を補完しない。SynQ Remote の一般説明・製品紹介は要約せず、顧客の反応や判断を理解するために必要な最小限だけ記載する。

## `## ネクストアクション` の書き方

文字起こしまたは既存メモに明示された合意・依頼・持ち帰りだけを書く。主体が明示される場合だけ `【株式会社クアンド側】` と `【顧客側】` に分け、明示的なアクションがなければ補完しない。

## 完了確認

- 会議と原本の対応が根拠をもって一意に決まっている。
- テンプレートの4見出しと順序を保ち、`## ネクストアクション` は `## 議事録` の直後にある。
- 重要な顧客情報が `【提案設計に関わる顧客理解】` に集約され、顧客の状態・制約・判断条件を会話の流れを追わずに把握できる。
- 顧客情報を薄めず、SynQ Remote の説明や推測した事実・アクションを混入させていない。
